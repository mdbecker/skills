# Consequence-grounded structural audit

Declare subsystem/repository scope, snapshot, included/excluded files, architecture,
public invariants, callers/tests/configuration, language and compatibility. Exclude
generated environments. Include tests/experimental code only when requested or
needed as evidence. Historical counts/locations require fresh inspection.

Inventory responsibility/state clusters, repeated algorithms, coupling and
coordinated-edit requirements; trace candidates through actual use. Report structure
only with a concrete maintenance/change-locality/testability/security/operational
consequence. File length, method count, data-only DTOs/protocols, adapters and cohesive
long routines alone do not establish a smell.

Diagnostic families: bloaters/data clumps, divergent change/shotgun surgery,
duplicated state/branching policies, inappropriate coupling and harmful dispensable
duplication. Choose the smallest complete remedy reducing real risk; registries,
typed values or adapters must remove rather than relocate complexity. Preserve
ordering/errors/APIs/schemas/security and compatibility. Sequence by dependency/risk.

Each finding: ID, family, location, structural evidence/consequence, preferred remedy,
protected invariants and needed behavioral validation. S3 = correctness/operational
risk; S2 = significant design risk; S1 = maintainability; S0 = observation. Do not
equate structural severity with fix urgency or Debate impact labels.

Deliver summary, ranked findings, file-by-file coverage including no-finding files,
incomplete inspections and dependency-aware remedies. No finding is bounded evidence,
not perfection. The separately referenced Python guide is not available in this
distribution; use only methodology supported by the pinned source excerpt.

# Adapt a method to another project

Read current instructions and identify the editing/build surfaces before choosing
commands. Record source authority and conflict rules, compatibility obligations,
protected behavior/evidence, allowed actions/data, prerequisites, canonical checks,
generated artifacts and host capabilities. Missing critical mappings are blockers
for the affected operation, not opportunities to guess historical defaults.

Use project-relative paths. Resolve installed helpers beside the bundled method
and run from the target project. Do not assume a language, vendor, check engine, table/issue identifiers,
source windows, model IDs or business categories. Use the [project mapping](project-profile.md).
The manifest helper alone has the retained Python 3.11+ runtime requirement.

Preserve the method's decisions, evidence requirements and ordering. Choose BDD
explicitly if the target project requires red-first behavior; do not silently
reorder an active Iterate feature. Map validation from authoritative tooling, not
from a source example. Keep review scope and engine distinct, and report actual
host support instead of translating a model/provider name by guesswork.

For reports record editable inputs, saved-evidence identities/hashes, build graph,
protected claims/cohorts/denominators/comparisons, permitted aggregate/suppression
rules, expected outputs, automated and visual/offline checks. A new pipeline or
new evidence acquisition is outside report assembly/maintenance.

Test both a reference case and a substantive separate-project case, including
failure and non-trigger requests. Static/installation checks do not prove host
invocation or quality. Record actual public artifact identities and disclose unavailable
engines, guides, data and historical artifacts. Distribute only authorized inputs.
